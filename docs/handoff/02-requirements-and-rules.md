# 梁文钟｜需求、规则与验收

状态：产品设计交接，非生产实现。下面的数据字段是语义要求，不规定最终序列化格式或技术栈。

## 一、已核实的价格规则快照

来源：https://api-docs.deepseek.com/zh-cn/quick_start/pricing/

核对日期：2026-10-21。

| 北京时间 | 状态 |
|---|---|
| 周一至周五（不含中国法定节假日）09:00–12:00、14:00–18:00 | 高峰，应用称“梁文峰” |
| 其余时间，包括周末及中国法定节假日全天 | 空闲，应用称“梁文谷” |

当前价格单位：人民币元 / 百万 Tokens。

| 模型 | 计费项 | 空闲 | 高峰 |
|---|---|---:|---:|
| deepseek-flash | 输入缓存命中 | 0.02 | 0.04 |
| deepseek-flash | 输入缓存未命中 | 1 | 2 |
| deepseek-flash | 输出 | 4 | 8 |
| deepseek-v4-pro | 输入缓存命中 | 0.15 | 0.30 |
| deepseek-v4-pro | 输入缓存未命中 | 4.5 | 9 |
| deepseek-v4-pro | 输出 | 13.5 | 27 |

上表只是核实快照，不是永久常量。当前各模型 Token 计费项在谷期均为峰期一半；Search / Fetch 是独立按次收费，不应纳入“全部费用减半”之类宣传。

对比必须指定基准：峰期是谷期的 2 倍；谷期较峰期低 50%。提醒指单价，不保证实际总费用，因为用量和缓存情况可能改变。若未来各计费项倍率不一致，不输出统一倍率，退化为“进入高峰 / 空闲价格时段”。

## 二、日期判定

1. 所有价格状态按 Asia/Shanghai 计算，不随设备所在地改变。
2. 优先应用经确认的具体日期覆盖规则；其次判断周末和法定节假日；其余周一至周五才匹配高峰时段。
3. 时段采用左闭右开区间：09:00 属峰期，12:00 属谷期，14:00 属峰期，18:00 属谷期。
4. 不将系统或第三方“是否工作日”结果直接等同于官方价格规则。当前官网文字明确周末为空闲，周六周日补班不自动改成峰期。
5. 日期数据应记录覆盖范围、来源、版本和有效性。法定节假日与放假调休安排的具体映射需核实，不把通用调休日历未经审核直接当计费日历。
6. 下次切换是状态真正变化的下一个时刻，不是下一个日期边界。周末、假期、跨年连续谷期应合并，不因午夜重复提醒。
7. 规则缺失或过期导致状态无法确认时显示“规则待更新”，不显示精确但未经确认的价格倒计时，并暂停相关价格提醒。单纯联网失败、但本地数据仍有效，不应停用有效规则。

## 三、功能需求

| 编号 | 要求 |
|---|---|
| F01 | 常驻 Mac 状态栏，默认“峰 / 谷＋剩余时间”，长时间使用小时或天，按分钟更新，不跳秒 |
| F02 | 点击状态栏展开小面板，再次点击或点击外部收起；不建立常驻主窗口 |
| F03 | 主面板仅显示状态、价格差异、倒计时和简短的下一切换信息 |
| F04 | 设置包含关闭 / 中等 / 强，默认中等；本地保存偏好 |
| F05 | 中等：切换一次通知＋短音一次，不循环，不阻塞工作 |
| F06 | 强：醒目提醒与持续提示，用户能手动停止；具体可实现方式需要按平台验证 |
| F07 | 提前提醒默认关闭；开启时首版用提前 5 分钟的简单选项，策略能更新偏移量 |
| F08 | 提醒文案必须明确贵或便宜，显示下一价格窗口或持续时间 |
| F09 | 设置中可查看规则来源、版本 / 更新时间与有效性，可检查更新 |
| F10 | 用户关闭提醒后仍可查看时钟；不因规则更新重新启用提醒或提高强度 |
| F11 | 启动、唤醒、系统时间或时区变化后重算当前状态和未来事件；不把历史切换集中补发 |
| F12 | 不要求账号、API Key 或后台持续网络连接；本地有效规则足以计算状态 |

## 四、职责拆分

| 层次 | 可配置内容 / 职责 |
|---|---|
| 价格规则 | 版本、生效时间、来源、时区、每周时段、具体日期覆盖、日历覆盖范围、模型与单价 |
| 提醒策略 | 进入峰 / 谷、切换前等阶段；偏移量；文案模板；语义样式；各强度的重复间隔及停止条件 |
| 通用机制 | 加载和校验规则、计算状态与下一事件、匹配策略、调用平台提醒能力、去重与停止 |
| 本地偏好 | 用户选择的强度、提前提醒开关；不被远程策略更新覆盖 |

配置不是远程代码。只支持有限、声明式的阶段、模板变量和提醒动作，避免为了“灵活”引入任意脚本系统。无须在首版提供可视化策略编辑器。

### 更新行为

- 内置可用版本；从应用控制的固定来源获取价格规则、日期数据和提醒策略。
- 校验格式、版本兼容性、生效时间、时段与日期合法性、引用关系及来源完整性。安全校验方式由实现方案提出。
- 使用一套相互兼容且完整的有效数据后再替换，不能启用只有一半成功的更新。
- 下载或校验失败保留有效旧版本；不能把未知内容当有效规则。
- 更新成功后取消过期计划、按新规则重算，避免重复通知；不因为更新本身模拟一次价格切换。
- 新规则若有未来生效时间，应到期启用，不提前改变当前价格状态。
- 日期规则不适用当前时间时进入待更新状态；恢复有效数据后重新安排未来事件。

### 通知样例

| 事件 | 标题 | 正文样例 |
|---|---|---|
| 进入谷期 | 低价时段开始 | 模型 Token 单价降低 50%。本次低价持续 2 小时。 |
| 进入峰期 | 高峰时段开始 | 模型 Token 单价为谷期的 2 倍。距离下次低价还有 4 小时。 |
| 提前提醒 | 还有 5 分钟进入高峰 | 模型单价即将上升。下一低价窗口为…… |

倍率、时间、持续长度都来自当前有效规则；上述数字仅为当前规则下的示例。强提醒应有明确的停止按钮，同一事件关闭后不再反复启动。

## 五、平台约束与待验证问题

- Mac：关闭面板仍提醒；主动退出应用后的提醒是否可达，必须在实现方案中说明，不能把“关闭面板”等同于“退出进程”。
- iOS：使用系统支持的通知与调度能力。后台规则更新时效、通知计划范围、专注模式 / 静音影响、强提醒能力均需验证；不承诺与 Mac 完全相同的持续闹铃体验。
- 规则更新可在启动、回到前台及主动检查时尝试；后台更新依平台能力，不能承诺手机始终实时获取。
- 当前官方价格页没有明确跨越切换时刻的请求按哪个时点判价。不得承诺“提前开始即可锁价”。
- 本轮未确定通知声音、强提醒是否抢焦点、重复间隔、最长持续时长、最低系统版本、分发渠道和技术栈。实现前给出最小可行方案，关键体验差异需明确。
- 不在本阶段安排自动任务、发送消息、连接开发服务或初始化代码仓库。

## 六、交付验收场景

1. 普通非节假日周三 08:59 为谷、09:00 为峰、12:00 为谷、14:00 为峰、18:00 为谷。
2. 周六全天谷；周六补班不自动变峰。
3. 规则表明确覆盖的法定节假日，即使周一也为谷。
4. 日期覆盖规则优先于每周默认规则，且能够通过更新改变。
5. 连续周末 / 假日无午夜伪切换、无每日重复价格提醒。
6. 设备位于其他时区，价格判断仍按北京时间，显示语义清楚。
7. 当前状态或下一切换涉及未覆盖日历时，不展示未经确认的精确结论。
8. 网络失败但有效规则存在，继续可用；坏格式或不兼容更新不破坏旧数据。
9. 未来生效的规则不提前启用；兼容更新成功后只安排新事件。
10. 同一切换只提醒一次；用户停止强提醒后不为该事件重新响铃。
11. 提醒关闭后不出通知；更新不改变本地强度。中等不循环，强提醒可以停止。
12. 提前提醒默认关闭；开启后使用策略偏移量，正式切换仍按策略提醒，不与历史事件混淆。
13. 唤醒或重启后恢复正确状态，不补发一串错过的通知。
14. 首版不含账号、API Key、统计、番茄钟或任务调度；正式 UI 不包含演示控件。
15. 在真实目标系统上验证通知权限、静音 / 专注模式和退出行为，并如实记录限制。

这些是待开发的验收要求，不代表当前交互稿已实现或通过这些检查。
