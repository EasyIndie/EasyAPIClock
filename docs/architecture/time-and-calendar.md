# 时间与日历

## 固定北京时间

DeepSeek 的峰谷定义写在「北京时间」上。应用固定使用 `Asia/Shanghai`：

```swift
Calendar(identifier: .gregorian) + TimeZone(identifier: "Asia/Shanghai")
```

- 不使用 `TimeZone.current`，设备在纽约、伦敦或东京都不改变判断。
- 中国当前不实行夏令时，固定 UTC+8；代码不依赖历史时区数据库。
- 界面上所有切换时刻、倒计时与日期摘要也按北京时间显示。

## 日期与分钟

| 类型 | 表示 | 用途 |
|---|---|---|
| `LocalDate` | `2026-10-23` | 节假日、覆盖范围、日期比较 |
| `MinuteOfDay` | `09:00` → 540 | 峰期窗口；`24:00` → 1440 只作结束 |
| `Date` | 绝对时刻 | 引擎输入/输出、通知排程 |

`LocalDate` 解码时会校验真实日历（例如 `2026-02-29` 无效），比较是字典序 `(year, month, day)`。

## 日期分类优先级

`ClockEngine.dayKind(for:)` 按以下顺序：

1. 命中节假日范围 → `.holiday(name:)`
2. ISO 周六/周日 → `.weekend`
3. 在 coverage 内 → `.weekday`
4. 否则 → `nil`（工作日无法确认）

因此：

- 节假日覆盖优先于每周窗口。
- 周六/周日无论是否调休上班，都是 `.weekend`。
- 超出覆盖范围的周六/周日仍然确认为谷；超出范围的工作日无法确认。

## 状态判定

- `.weekend` / `.holiday`：全天 `.valley`。
- `.weekday`：分钟落在某个 `[start, end)` 窗口内 → `.peak`，否则 `.valley`。
- 未知日期 → `nil`。

秒级边界：`11:59:59` 是峰，`12:00:00` 是谷；`08:59:59` 是谷，`09:00:00` 是峰。

## 下次切换算法

每天可能发生变化的时刻只有：

- 每个峰期窗口的开始与结束；
- 次日 00:00。

引擎从「今天 00:00」开始逐日向前（最多 400 天），收集严格晚于当前时刻的候选边界，按时间排序，取第一个 **状态与当前不同** 的边界。

```
for day in today ... today+400:
    if day 无法确认: return 未确认
    for boundary in candidates(day) where boundary > now:
        if state(boundary) != current:
            return boundary
```

这带来几个重要性质：

- **午夜不产生伪切换**：如果 00:00 前后都是谷，状态没有变化，不会报告切换。
- **周末/假期合并**：周五 18:00 的谷会一直延续到周一 09:00（或假期后的工作日 09:00）。
- **跨年**：12 月 31 日晚到次年 1 月 4 日（若有假期）会合并，只要日历覆盖足够。
- **覆盖不足**：搜索途中遇到无法确认的工作日 → 返回未确认，而不是跳过它猜测。
- **窗口结束**：找到切换后，再向后找一次变化，得到新窗口的结束时刻（用于「本次低价持续 2 小时」「距离下次低价还有 4 小时」）。若下一次无法确认，则省略时长文案。

### 当前窗口起点

从当前时刻向后搜索最近的候选边界 `b`，满足：

```
state(b) == current  &&  state(b - 1s) != current
```

这样周五 18:00 开始的谷期，其起点是周五 18:00，而不是周六 00:00。若窗口起点在覆盖范围之前，返回 `nil`（不猜测）。

## 覆盖语义

`CalendarRules.coverage` 是 **含首尾** 的连续日期范围。

| 情况 | 当前状态 | 下次切换 | 提醒 |
|---|---|---|---|
| 当前工作日超出覆盖 | 未知 | 未知 | 暂停 |
| 当前周末超出覆盖 | 谷（可确认） | 未确认（下个工作日未知） | 暂停 |
| 当前在覆盖内，但下次切换越过覆盖 | 已知 | 未确认 | 暂停 |
| 覆盖过期但网络失败 | 同上；继续使用本地数据并提示更新 | — | — |

界面文案：

- 状态未知：`待确认` / 具体问题 / 倒计时 `—` / `更新规则后恢复价格提醒`
- 状态已知但切换未确认：正常显示峰/谷，但倒计时 `—`，底部 `提醒暂停`
- 问题文案：`日期数据仅覆盖至 2026年12月31日` 或 `1月5日 的日期规则待确认`

## 价格倍率

`PriceComparison` 从所有模型的全部计费项推导：

- 谷期价为 0 且峰期价为 0 → 跳过；
- 谷期为 0 但峰期 > 0 → 无法给出统一倍率 → `.mixed`；
- 每个计费项计算 `peak / valley`，统一到 6 位小数；
- 全部相同 → `.uniform(multiple:)`，并给出 `valleyPercentLower = (1 - 1/m) × 100`（保留 1 位）；
- 任一不同 → `.mixed`，界面只显示「进入高峰/空闲价格时段」。

当前数据全部为 2 倍，所以显示「2 倍」与「低 50%」。**不要**把这两个数字写死在 UI 或通知文案里。

## 为什么不用「工作日日历」

第三方工作日/调休日历回答的是「是否上班」，不是「是否峰期」。官方文字明确：

> 北京时间周一至周五（不含中国法定节假日）9:00–12:00、14:00–18:00 为高峰时段；其余时段，包括周末及中国法定节假日全天均为空闲时段。

因此补班周六仍为谷。若未来官方修改规则，应通过新的价格/日历规则包表达，而不是改变解释逻辑。
