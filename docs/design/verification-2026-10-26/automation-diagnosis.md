# 自动截图失败诊断（2026-10-26）

## 确认的事实

- 谷蹬进程 PID 62425 从 06:41:50 运行，磁盘 ad-hoc 二进制最后修改于 06:57:53。make run-mac 的 open 没有替换已运行进程，先前“已启动优化版”缺少进程重启证据。
- 按完整应用路径执行 cua.getApp 在约 5.8 秒后返回 -10005 timeoutReached。此时尚未执行 getScreenshot，故直接故障位于应用连接/初始观察阶段，而非已确认的图像编码或写盘故障。
- 1 秒谷蹬线程采样的主线程处于 NSApplication.run → CFRunLoop → mach_msg 等待，未发现此次采样中的主线程死锁或忙循环。
- 同期 Computer Use 服务仍存活；15 秒采样中可见 AXUIElement 属性读取及等待，但服务业务符号未公开，无法据此确定具体哪个属性或条件超时。
- 上轮 Finder 可截图，说明不能把问题概括成全局截图能力完全失效；谷蹬是 LSUIElement=true 的 MenuBarExtra(.window) 应用，未展开时没有常驻主窗口。
- bundle ID 对应多个本地构建路径会产生独立的歧义错误；使用完整路径绕过该歧义后仍超时，故歧义不能单独解释本次超时。

## 待验证假设

最可能是 Computer Use 对菜单栏临时浮层的连接/窗口识别条件未满足。需要对比“浮层保持展开”和“浮层关闭”时同一路径 getApp 的结果，才可确认。另需重启到当前二进制后复测，排除旧进程和磁盘构建不一致的干扰。

不应为了自动化截图而移除 LSUIElement 或给正式产品增加常驻窗口。没有修改 TCC、系统权限或应用代码。

## 面板手动展开后的对照验证

用户回复「已展开」后，相同完整路径 cua.getApp 在 2.59 秒内成功返回原生界面树；getScreenshot 在 0.16 秒内成功。设置按钮点击、设置截图（0.14 秒）和返回主面板均成功。截图已保存为 04-expanded-panel.jpg 与 05-connected-settings.jpg（该旧进程截图不作为最新优化版的验收）。未更改任何偏好，最终保持主面板展开。

结论：当前可复现故障在未展开的菜单栏应用连接/窗口发现阶段；展开浮层后，界面读取、截图和面板内操作链路正常。无法从外部证据进一步断言服务内部具体哪一条件判断有缺陷。后续验收先确保浮层已展开，再绑定完整路径；不要把应用库存遗漏当作进程未启动，不要反复重建来处理连接超时。

另一个独立问题是运行旧进程：make run-mac 只 build + open，不能保证重启；必须确认退出旧实例后重新启动，才能验收磁盘上的最新二进制。此前“优化版已启动”的表述已被本次进程时间证据纠正。
