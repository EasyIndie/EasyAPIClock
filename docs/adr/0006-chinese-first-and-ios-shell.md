# ADR-0006：中文优先，iOS 只提供验证外壳

- 状态：已接受
- 日期：2026-10-23
- 决策者：项目维护者

## 背景

产品、文案与设计基准都是中文；首版范围包含 macOS 与 iOS，但只有 Mac 界面经过确认。iOS 的页面结构、通知能力与强提醒体验尚未设计。过早投入双语与 iOS 视觉会分散对核心正确性的注意力，也容易产生“看起来已完成”的错觉。

## 决策

1. v0.1 界面仅中文；所有用户可见文案集中在 `ClockText` 与 `ReminderCopy`，便于后续迁移。
2. 不在视图里散落用户可见字符串常量；通知文案必须由 facts 生成。
3. `Apps/iOS` 只提供只读外壳：
   - 展示当前状态、价格行、倒计时与日期摘要；
   - 明确标注「iOS 页面尚未设计确认」；
   - 不请求通知权限，不包含设置；
   - 用于保证核心跨平台编译与验证。
4. 不在 README、设计文档或发布说明中声称 iOS 已设计/已完成。
5. 本地化、iOS 正式交互、强提醒浮层都进入 `TASKS.md`，需要独立设计与验证。

## 后果

正面：

- 首版聚焦规则正确性、菜单栏体验与通知可靠性。
- 避免发明未经确认的 iOS 设计。
- 文案集中，未来加英文时改动面小。
- iOS 目标持续参与 CI，防止核心退化为 macOS-only。

代价：

- 国际用户使用门槛较高。
- iOS 目标当前价值有限，可能被误认为“已支持”。
- 中文文案直接写在 Swift 中，迁移到 String Catalog 需要一次重构。

## 备选方案

- **首版即双语**：会延迟核心验证，且英文文案需要产品审阅。
- **隐藏 iOS target**：CI 不再验证跨平台编译，未来接入成本更高。
- **自行设计 iOS 页面**：违反交接包的范围约束。
- **用 WebView 复用设计稿**：不是原生体验，通知与后台能力也受限。

## 后续

1. 把文案迁移到 String Catalog，提供英文；日期/时长使用本地化格式。
2. 完成 iOS 交互设计与平台通知验证后，再替换只读外壳。
3. 若 iOS 长期不推进，在 README 中明确标注为“实验目标”，避免误导。
