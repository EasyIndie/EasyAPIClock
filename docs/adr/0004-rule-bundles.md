# ADR-0004：声明式规则包、SHA-256 清单与暂存安装

- 状态：已接受
- 日期：2026-10-23
- 决策者：项目维护者

## 背景

价格、节假日与提醒策略会变化，不能每次都发版。更新来源在网络另一端，必须满足：

- 不执行远程代码；
- 价格、日历、策略可以分别维护，但必须成套生效；
- 下载失败或数据损坏不能破坏可用状态；
- 未来生效的规则不能提前改变当前价格；
- 更新不能覆盖用户偏好；
- 维护者能审计、复现、回滚。

## 决策

1. 规则包 = `manifest.json` + 价格 JSON + 日历 JSON + 提醒策略 JSON。
2. 三个文件各自有 `schemaVersion`、`version`、`source`；manifest 记录文件名、SHA-256、`publishedAt`、`effectiveFrom`、`bundleVersion`。
3. 安装前完成：
   - manifest 结构校验；
   - 文件名安全校验（禁止路径、`..`、隐藏文件）；
   - 每个文件的 SHA-256；
   - 三份 JSON 解码与完整语义校验；
   - 时区/覆盖/重叠/倍率可用性检查。
4. 先写入 `staging-<UUID>/`，重新加载校验通过，再替换 active 或 pending 目录。失败删除 staging，旧版本不动。
5. `effectiveFrom <= now` → active；否则 → pending，达到时间后提升。
6. 更新服务只在远端 `publishedAt` **严格晚于** 当前版本时安装，避免降级/重放。
7. 默认只允许 HTTPS（localhost 开发例外）；使用 `no-cache` 请求。
8. 不执行远程脚本、表达式或模板代码；提醒文案由本地代码从 facts 生成。
9. `liangwen-rules manifest` 负责重算校验和；CI 重算后要求 git diff 为空。

## 完整性 vs 真实性

SHA-256 能发现传输损坏、半套文件、意外编辑，**不能**证明发布者身份。当前信任根是：

- HTTPS；
- 仓库与发布账号的控制权；
- 用户选择的应用分发渠道。

因此当前不宣称“防篡改”，只宣称“完整性校验”。

## 后果

正面：

- 更新失败时行为可预测，最坏回退内置规则。
- 不存在“价格更新成功、日历更新失败”的半套状态。
- 未来生效规则自然支持，不需要客户端时钟技巧。
- 数据可读、可 diff、可由 CI 校验。

代价：

- 每次手工修改 JSON 后必须重算 manifest；CI 会拦截遗漏。
- 没有签名，恶意更新源仍可发布恶意但格式合法的规则（例如把全天设为峰）。
- 没有版本历史；回滚需要发布新包或删除本地 active 目录。
- manifest 与文件同源，若托管目录被替换，客户端只能依赖 HTTPS。

## 备选方案

- **单个 JSON**：简单，但无法独立更新价格/日历/策略，也更容易出现半套语义。
- **远程 JavaScript / JSONata / 模板**：灵活，但引入代码执行与供应链风险，违背产品边界。
- **现在就上 Ed25519**：更安全，但需要密钥管理、轮换、离线签名流程；首版先保留清晰升级路径。
- **Sparkle 式应用自动更新**：更新的是代码，不是数据；与规则数据更新目标不同。
- **服务端计算状态**：需要账号/网络，违背离线定位。

## 后续

1. 为 manifest 增加 Ed25519 签名与内置公钥；校验签名后再解析文件。
2. 设计密钥轮换与撤销；文档化离线签名步骤。
3. 规则托管到带版本标签的静态路径，保留上一版用于回滚。
4. 评估“发布前自动抓取官方页面 diff”的维护工具。
