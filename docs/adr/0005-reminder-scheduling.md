# ADR-0005：确定性事件 ID、只排未来事件、强提醒有界重复

- 状态：已接受
- 日期：2026-10-23
- 决策者：项目维护者

## 背景

提醒系统最常见的问题是：

- 每分钟刷新导致重复排程；
- 睡眠/重启后补发一串过期通知；
- 强提醒无限响铃、无法停止；
- 规则更新或强度切换后重复提醒同一事件；
- 需要持久化“已发送”账本，但账本损坏后又重复。

平台能力有限：本地通知不能保证穿透专注模式，也不能可靠地无限重复并随时停止。

## 决策

1. 计划器是纯函数：`ReminderPlanner(now, preferences, policy).plan(for: snapshot)`。
2. 只产生 `fireDate > now` 的事件；过去的切换、错过的提前提醒直接丢弃。
3. 事件 ID 由事件类型 + 切换时刻（+ 提前偏移）确定性生成：
   - `t:<epoch>`
   - `a:<lead>:<epoch>`
4. 通知请求 ID 加 `lw.` 前缀；强提醒重复加 `.rN`。相同 ID 会替换 pending，不会重复。
5. 不维护“已发送账本”。去重由“确定性 ID + 只排未来”共同保证。
6. 强提醒预排有界重复（默认 30 秒 × 10），使用通知分类提供「停止提醒」动作；停止时移除该事件所有 pending 与已送达通知。
7. 计划变更用签名比较，避免每分钟重置重复计时；签名包含授权、规则版本、事件内容。
8. 提前提醒在强模式下不重复。
9. 应用只使用系统通知；不自建后台守护进程，不请求 Critical Alerts。

## 后果

正面：

- 无持久化状态机，重启后行为可预测。
- 同一事件不会因刷新、强度切换或规则重载而重复排程。
- 睡眠唤醒不补发历史。
- 强提醒有明确上限与停止路径。

代价：

- 无法记录“用户已读”或跨设备同步。
- 系统若丢弃/延迟通知，应用无法感知或补偿。
- 停止操作在应用被终止时的行为未验证；重复通知已预排，若系统未执行移除可能继续。
- 强提醒不是独立浮层，视觉冲击有限。

## 备选方案

- **持久化账本**：能记录已发送，但需要一致性、迁移与清理；当前需求不需要。
- **`UNTimeIntervalNotificationTrigger(repeats: true)`**：无法在有限次数后自动停止，也不便整体取消，容易变成骚扰。
- **自定义 NSPanel + 循环声音**：更醒目，但呈现方式未设计/未批准，且增加窗口与音频生命周期复杂度。
- **后台守护进程**：超出范围，增加权限与分发负担。
- **服务端推送**：需要账号与网络，违背离线定位。

## 后续

- 在真实设备验证：前台/后台/退出、Focus、静音、睡眠唤醒、停止动作。
- 若验证表明系统通知不足，评估经设计确认的独立浮层，并新增 ADR。
- 评估是否需要在设置中提供“重置提醒状态”。
