## 为什么要单独验证

单元测试只能证明“计划正确”，不能证明系统真的送达。以下行为依赖 macOS/iOS 版本、权限、Focus、静音、通知中心策略、应用生命周期与签名状态：

- 通知是否显示、是否响铃；
- 强提醒重复是否能被“停止”打断；
- 面板关闭、进程退出、系统睡眠后是否仍送达；
- 唤醒后是否补发历史通知；
- 权限被拒绝/撤销后的行为；
- 点击通知是否激活应用（当前不会自动展开面板）。

## 日志（辅助取证）

应用使用 `OSLog`，不包含账号、Token 或价格请求内容。验证时在 Console.app 中选择对应设备，过滤：

```
subsystem:com.easyindie.easyapiclock
```

（v0.1.0 及更早构建使用旧子系统 `app.liangwen`，仅作历史记录。）

分类：

- `clock`：启动、刷新、计划事件数、规则更新结果；
- `notifications`：授权状态、重排、安排失败、停止强提醒；
- `rules`：安装 active/pending、已安装规则损坏回退、待启用规则到期。

日志只用于定位系统通知/更新问题，不作为“已送达”的唯一证据；仍需记录通知中心与声音的实际表现。

## 如何制造一个近期的切换

三种方式，按风险从低到高：

1. **等待真实边界**（推荐）：工作日 08:59、11:59、13:59、17:59 前 1–10 分钟启动应用。默认中等提醒会在切换时触发。
2. **本地规则源（推荐）**：

```bash
# 生成一个 3 分钟后进入峰期的测试包，并启动 localhost 服务器
make serve-test-rules

# 测试提前提醒时，让峰期在 7 分钟后开始
Scripts/serve-test-rules.sh --lead-minutes 7

# 周末/任意一天只验证规则安装、重复检查与离线回退
Scripts/serve-test-rules.sh --install-only
```

脚本会复制 `Rules/` 到 `.build/test-rules`，只修改临时包，重新计算 manifest，并打印启动命令。另开终端：

```bash
make build-mac-adhoc
GUDENG_RULE_SOURCE=http://127.0.0.1:8765 \
  .build/DerivedDataAdhoc/Build/Products/Debug/GudengMac.app/Contents/MacOS/GudengMac
```

然后在设置中点击「检查规则更新」。测试包只用于验证，不要提交或发布。**周末恒为谷，脚本会拒绝生成；请在工作日运行。** 测试结束后清理 active 规则，回退内置版本：

```bash
rm -rf ~/Library/Containers/com.easyindie.easyapiclock/Data/Library/Application\ Support/Gudeng/Rules/active
```
3. **修改系统时间**：可以验证唤醒/重算，但会影响其他应用与通知计时；测试后立即恢复，并记录风险。

## 2026-10-27 · 预览通知无横幅/声音的排查记录

### 建议排查顺序

1. **确认应用预览确实启动。** 设置页按钮进入「立即停止预览」且出现测试说明，证明应用开始执行预览流程；等待预览结束或手动停止。按钮状态只说明应用侧流程，不等于系统已经呈现通知。
2. **检查谷蹬的系统通知设置。** 在“系统设置 → 通知 → 谷蹬”确认“允许通知”、横幅/通知中心位置和“播放通知的声音”已开启，并记录横幅样式。设置关闭时，先处理权限，不要通过重复点击预览来判断。
3. **检查当前专注模式。** 在控制中心确认当前 Focus 状态。专注模式可能抑制或延迟通知，即使谷蹬已列入该模式的允许 App，也不能据此认定一定会显示/发声。若要做对照复测，可临时关闭当前模式，完成单次预览后恢复原状态，并记录前后状态；不要关闭不相关的模式或改动通知权限。

6. **核对结束清理。** 预览最多持续 10 秒，或在手动停止/关闭面板/退出时结束。结束后确认预览专用 `gudeng.preview.*` pending/delivered 请求清理，正式提醒排程数量未改变。
