## 为什么要单独验证

单元测试只能证明“计划正确”，不能证明系统真的送达。以下行为依赖 macOS/iOS 版本、权限、Focus、静音、通知中心策略、应用生命周期与签名状态：

- 通知是否显示、是否响铃；
- 强提醒重复是否能被“停止”打断；
- 面板关闭、进程退出、系统睡眠后是否仍送达；
- 唤醒后是否补发历史通知；
- 权限被拒绝/撤销后的行为；
- 点击通知是否激活应用（当前不会自动展开面板）。

## 日志（辅助取证）

应用使用 `OSLog`，不包含账号、Token 或价格请求内容。验证时在 Console.app 中选择对应设备，过滤：

```
subsystem:app.liangwen
```

分类：

- `clock`：启动、刷新、计划事件数、规则更新结果；
- `notifications`：授权状态、重排、安排失败、停止强提醒；
- `rules`：安装 active/pending、已安装规则损坏回退、待启用规则到期。

日志只用于定位系统通知/更新问题，不作为“已送达”的唯一证据；仍需记录通知中心与声音的实际表现。

## 如何制造一个近期的切换

三种方式，按风险从低到高：

1. **等待真实边界**（推荐）：工作日 08:59、11:59、13:59、17:59 前 1–10 分钟启动应用。默认中等提醒会在切换时触发。
2. **本地规则源（推荐）**：

```bash
# 生成一个 3 分钟后进入峰期的测试包，并启动 localhost 服务器
make serve-test-rules

# 测试提前提醒时，让峰期在 7 分钟后开始
Scripts/serve-test-rules.sh --lead-minutes 7

# 周末/任意一天只验证规则安装、重复检查与离线回退
Scripts/serve-test-rules.sh --install-only
```

脚本会复制 `Rules/` 到 `.build/test-rules`，只修改临时包，重新计算 manifest，并打印启动命令。另开终端：

```bash
make build-mac-adhoc
LIANGWEN_RULE_SOURCE=http://127.0.0.1:8765 \
  .build/DerivedDataAdhoc/Build/Products/Debug/LiangWenMac.app/Contents/MacOS/LiangWenMac
```

然后在设置中点击「检查规则更新」。测试包只用于验证，不要提交或发布。**周末恒为谷，脚本会拒绝生成；请在工作日运行。** 测试结束后清理 active 规则，回退内置版本：

```bash
rm -rf ~/Library/Containers/app.liangwen.mac/Data/Library/Application\ Support/LiangWen/Rules/active
```
3. **修改系统时间**：可以验证唤醒/重算，但会影响其他应用与通知计时；测试后立即恢复，并记录风险。

## 已知限制（验证时重点确认）

- 强提醒是重复通知，不是浮层；无法覆盖专注模式/静音。
- 没有 Critical Alerts 权限，不能保证穿透系统静音。
- 应用退出后不会重新排程；已排定通知可能仍送达。
- 规则更新只在启动/刷新/手动检查时发生，不承诺后台实时。
- 当前通知点击只激活应用，不会自动展开面板。
- ad-hoc 签名的开发构建与正式签名构建在通知/沙盒行为上可能不同。
