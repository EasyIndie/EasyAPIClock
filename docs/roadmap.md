# 路线图

## 当前：v0.1.0 工程脚手架（2026-10-23）

已完成：

- 纯逻辑规则引擎、北京时间与节假日语义、下次真实切换。
- 规则包完整性、原子安装、未来生效、失败回退。
- 提醒计划与文案、macOS 菜单栏应用、内嵌设置、本地偏好。

明确未完成：公证、真实设备通知验证、iOS 设计、英文界面、规则数字签名。

## M1：可发布（P0）

目标：可以对外提供一个可信、可安装的 macOS 预览版。

- [ ] 真实设备通知矩阵验证（Focus、静音、睡眠、退出、强提醒停止）；`make serve-test-rules` 已提供测试规则包。2026-10-24 macOS 27 已完成界面/更新/退出/权限拒绝，通知投递与 macOS 14/15 待测。
- [x] Release 打包骨架：`make package-mac`、Release 通用构建、手动 Release artifact workflow。
- [x] Developer ID 签名、Hardened Runtime、通用二进制 zip/dmg；必须从 GUI 会话运行 `make package-mac`。
- [ ] 公证：配置 `notarytool` profile，staple 并通过 `spctl`。
- [x] 应用图标：1024pt 峰谷分色时钟，AppIcon 全套尺寸。
- [x] README 真实截图：主面板与设置页（截图机通知未授权，README 有说明）。
- [x] 规则托管：GitHub `rules` 分支 + `Rules` workflow 自动发布。
- [ ] 一次成功更新与一次坏包回退的真机演练。
- [ ] 版本号、CHANGELOG、发布说明、隐私说明。

发布门槛：`make check` 通过；A15 有记录；公证后通过 `spctl`。

## 开放问题

1. 强提醒是否值得做独立浮层？需要设计确认与平台验证。
2. 应用退出后已排定通知的可达性如何向用户解释？
3. 规则包签名密钥由谁持有、如何轮换？
4. 分发渠道：Developer ID 直发、Mac App Store，还是两者？
5. 2027 年节假日安排发布前，跨年用户体验如何提示最清晰？
6. 是否需要“检查更新”之外的自动检查频率？后台能力如何限制？
7. 是否提供锁定到某个历史规则包的能力（用于审计/复现）？
8. 首次启动即请求通知权限是否合适，还是等用户第一次打开设置/选择强度时再请求？

## 明确不做

- 账号、API Key、Token 统计、消费分析。
- 番茄钟、任务管理、Agent 集成、自动切换模型。
- 主界面完整价格表、图表、复杂日历。
- 硬件配网/设备管理。
- 可视化规则编辑器。
- 在未授权情况下发布、上架或购买服务。
